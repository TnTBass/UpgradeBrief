## Recurrence controls

- Strict per-CVE parsing consumes affected and fixed builds, severity, deployment conditions, and all CVEs. Unknown trailing guidance, mixed products, missing sections, and incomplete CVE coverage fail closed.
- Recognized inventory additions may prepend newer release blocks containing explicit CVE fixes or dependency version changes. All existing guidance must remain identical, and normal product-wide CVE coverage still runs. Changed historical entries or unsupported formats require review. Inventory additions are reported separately from wording equivalence.
- Preparation failures persist an article-specific diagnostic. Investigations include the diagnostic in their identity and update a marked latest-occurrence block without discarding reviewer notes.
- The scheduled feedback workflow independently checks validated snapshot age on main and the published site's health endpoint. It warns at 36 hours, escalates at 72 hours, treats unavailable publication health as critical, deduplicates each severity for the same snapshots, and closes the investigation when both recover. A successful repair workflow or fresh main cannot hide a stale published catalog.

- Scheduled refreshes have a 35-minute timeout and run the full application, adapter, catalog, lint, TypeScript, and build verification on the freshly generated data before committing to main. Failed verification logs are retained for investigation.
- Main push events verify the published commit and catalog hash against the checked-out snapshot. Scheduled refreshes also invoke that verification directly after committing, covering bot pushes that do not trigger another workflow. This catches deployment failures independently of build success; a newer main push cancels a superseded publication check.

The refreshed snapshot also exposed tests coupled to the old recommended release and retired hotfix wording. Informational-source urgency is tested independently of unrelated new CVEs, current ONE remediation follows the reviewed source, and editorial journey tests use the archived reviewed destination. The runtime guard continues to withhold editorial guidance for an unreviewed destination such as 13.1.2; it is not widened automatically by catalog refresh.

## Product isolation assessment

Keep publication atomic for this recovery. Several advisories cover both standalone products and embedded components; inventory, source, and finding continuity are cross-product checks. Publishing only unaffected products safely requires explicit per-product freshness, source-to-product dependency groups, and transactional validation of each group. Simply catching a product's failure and publishing the rest could mark stale security data as fresh. That architecture is a separate follow-up, with acceptance tests for shared VBR/Enterprise Manager and ONE/VRO sources, retained stale findings, and visible per-product freshness.
